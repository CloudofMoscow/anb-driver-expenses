## Исходная версия и назначение

- Рабочая ветка по прямому выбору владельца: `codex/foundation-v1`.

- Название системы: **ANB Fleet Finance**. Это PWA для управления рейсами, автопарком, расходами, дебиторской задолженностью, взаиморасчётами с водителями и доходностью.
- Текущий масштаб по архитектурному документу: одна компания, примерно пять машин и водителей, несколько сотрудников офиса. В схеме предусмотрен `organization_id`, но это ещё не готовая многокомпанийская SaaS-платформа.

При подготовке контекста код приложения не изменялся. Добавлен этот документ и дополнены инструкции `AGENTS.md`. Коммитов и отправки изменений в GitHub не выполнялось.

## Стек и запуск

- Node.js **24+**, JavaScript ESM, встроенный HTTP-сервер и `node:sqlite`.
- SQLite в WAL-режиме, внешние ключи включены; миграции применяются автоматически при открытии базы.
- Обычные HTML/CSS/JS без React, TypeScript, Vite и отдельной сборки frontend.
- Единственная прямая npm-зависимость: `web-push` **3.6.7**. В репозитории есть `pnpm-lock.yaml`; README описывает установку через npm.
- Интерфейс и API обслуживаются одним Node-процессом с одного origin.

Основные команды из корня репозитория:

```powershell
npm install
npm run demo
npm test
npm run check
```

Другие команды: `npm start`, `npm run dev`, `npm run phone`, `npm run backup`.

Демо использует отдельный игнорируемый каталог `demo-data/`, создаёт тестовый автопарк и пользователей:

```text
офис:     owner / anb-demo-2026
водитель: driver1 / driver-demo-2026
```

Это публичные демонстрационные реквизиты из репозитория, а не рабочие пароли. Обычный запуск запрещает известный демопароль. При первом рабочем запуске нужны `ANB_BOOTSTRAP_LOGIN` и `ANB_BOOTSTRAP_PASSWORD`.

Для проверки в этом чате демо запущено на `http://127.0.0.1:8796` с `NODE_ENV=development`, `ANB_HOST=127.0.0.1`, `ANB_DISABLE_PUSH=1`. Сервер — временный процесс, его доступность нужно проверять в следующем чате. Стандартный порт приложения — 8787; команда доступа с телефона использует 8788.

## Кабинеты и основные сценарии

**Офис:** Обзор → Рейсы → Расходы → Водители → Автопарк → Заказчики → Доходность → Настройки. Водители разделены на балансы, переводы, ставки и корректировки; автопарк — на сцепки, транспорт и постоянные расходы. Есть общий поиск, быстрые действия, история проверок и управление доступом.

**Водитель:** Главная → Рейс → Расходы → Сообщения. Главное действие зависит от состояния рейса. Для начала и завершения нужны время, показание одометра и оригинал фотографии. Для расхода нужны сумма, источник денег, комментарий и чек. В «Сообщениях» отображаются уведомления офиса и состояние очереди; это не полноценный двусторонний мессенджер.

Основной фактически используемый переход рейса:

```text
assigned → in_progress → pending_review → confirmed
```

Схема также допускает `draft`, `awaiting_loading`, `completed_by_driver`, `needs_explanation`, `closed`. Наличие статуса в CHECK-ограничении не означает наличие полноценного UI-перехода в него.

Начало рейса проверяет актуальность сцепки и отсутствие другого активного рейса с тем же водителем, тягачом или тралом. При смене состава сцепки ещё не начатые задания переносятся на новый период; исторические рейсы сохраняют снимок состава.

Офис подтверждает рейс после проверки всех расходов. Ошибки пробега и времени исправляются до подтверждения с причиной и записью старого и нового значений в аудит.

## Финансовые правила, которые нужно сохранять

1. Все деньги хранятся и передаются **целыми копейками**. На границе формы использовать `rublesToKopecks`; не выполнять финансовые расчёты в дробных рублях.
2. Первоначальная ставка рейса, корректировки ставки, поступления заказчика, начисления водителю и фактические переводы — разные сущности.
3. Оплата заказчика уменьшает долг; повторно увеличивать на неё выручку нельзя.
4. Доплаты, штрафы и скидки записываются отдельно от исходной ставки.
5. Ошибочные денежные записи сторнируются с причиной; история не удаляется.
6. Подтверждение рейса фиксирует зарплату по пробегу и суточные по календарным дням включительно. Приоритет ставки: особая ставка рейса → ставка водителя → общая ставка компании. Использованная ставка сохраняется в начислении.
7. Для незакрытого рейса суточные учитываются предварительно; после подтверждения предварительный расчёт заменяется сохранённым начислением.
8. Один перевод водителю может содержать зарплату, суточные, аванс на расходы и компенсацию личных расходов. Возвраты имеют обратное направление.
9. Чистый баланс водителя: зарплата + суточные + компенсация + общие корректировки − неиспользованный аванс, с учётом выплат. Положительный баланс означает долг компании водителю.
10. Постоянные расходы распределяются по месяцам и дням периода. Для `equal_months` целая сумма делится на календарные месяцы с распределением остатка копеек.
11. Отчёт доходности уже включает завершённые водителем рейсы `pending_review` и `needs_explanation` как **предварительные**, наряду с `confirmed` и `closed`. Непроверенные расходы не исключаются, кроме `rejected`; предварительная зарплата рассчитывается отдельно. Нельзя считать весь показанный итог окончательно подтверждённым.
12. Финансовые даты группируются по Москве: UTC+3 в серверном коде и SQL. Браузерные поля даты/времени преобразуются из локального времени устройства в ISO.

## Доступ, файлы и офлайн

- Роли: `office` и `driver`; проверка выполняется на сервере. Данные организации проверяются при обращении к сущностям.
- В водительском DTO по умолчанию отсутствуют ставка рейса, заказчик, договоры и денежные расчёты водителя. `ANB_DRIVER_COMPENSATION_VISIBLE=1` — резервная возможность, а не включённая функция. Без отдельного решения владельца её не включать.
- Cookie сессии: HttpOnly, SameSite=Strict; Secure включается в production. В базе хранится SHA-256 токена, пароли — scrypt. Есть ограничения попыток входа и параллельной проверки паролей, отзыв сессий.
- Файлы выдаются через авторизованный `/api/files/:id`, не как публичный каталог. Проверяются назначение, MIME и сигнатура. Лимит одного файла — 12 МБ; действуют дневные и общая квоты. Оригиналы сохраняются на диске.
- Офлайн-очередь привязана к пользователю и хранит Blob файла вместе с устойчивым `clientMutationId`. Сначала загружается файл, затем выполняется операция. После потери ответа повтор используется для получения уже записанного результата.
- Операции идут по порядку. Отклонённая сервером команда блокирует зависимые действия. Ошибочный локальный старт можно отменить с его зависимой цепочкой.
- `financial-mutation.js` сохраняет неопределённые операции при сети/5xx; детерминированный 4xx позволяет исправить ввод. Если изменён черновик после потерянного ответа, сначала согласуется прежняя команда.
- Service worker не кэширует `/api/`; данные водителя сохраняются отдельным пользовательским кэшем. Выход и очистка устройства учитывают неотправленную очередь.
- Открытые кабинеты обновляются примерно каждые 30 секунд. Уведомления сначала пишутся в БД, push — дополнительный канал. До пяти попыток доставки; устаревшие подписки отключаются.
- Геопозиция отправляется для активного рейса по разрешению пользователя. В видимом приложении предусмотрена проверка раз в пять минут. Непрерывный фоновый трекинг закрытой PWA не реализован.

## Данные и эксплуатация

Рабочая база по умолчанию: `%LOCALAPPDATA%\ANB Fleet Finance\data\anb.sqlite`; закрытые файлы — в `uploads` внутри каталога данных. Это отдельное место от исходников и демо. Переменные `ANB_DATA_DIR`, `ANB_DATABASE_PATH`, `ANB_UPLOADS_DIR` переопределяют пути.

Для постоянной эксплуатации нужны отдельный работающий Node-сервер, домен/HTTPS и обратный прокси. GitHub Pages обслуживает только старый статический прототип. `ANB_TRUST_PROXY=1` разрешён при loopback-привязке сервера. База должна быть на локальном диске, вне OneDrive и сетевых каталогов.

Backup использует SQLite backup API, копирует файлы, переводит старые абсолютные пути в переносимые и сверяет размер/SHA-256 каждого вложения. Само создание локальной копии не организует её внешнее хранение и регулярные испытания восстановления.
