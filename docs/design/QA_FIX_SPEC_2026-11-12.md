# Спецификация исправлений QA — 12 ноября 2026

Статус: **вариант 1, готов к реализации разработкой**. Основание: F07/F08/F10/F11 из `docs/QA_AUDIT_2026-11-12.md`. Это спецификация поведения, не отчёт об уже выполненной реализации. Дизайн владеет CSS; JS/HTML/ARIA и тесты реализует чат «Разработка».

Сохраняем стек, бренд ANB, существующие компоненты, токены, финансовые правила, роли и офлайн-очередь. Не добавляем полноценный мессенджер или новые бизнес-сущности.

## F07 — история сообщений водителя

- Раздел «Сообщения», заголовок списка «Все сообщения»: показывать непрочитанные **и прочитанные** уведомления из доступной истории, новые сверху по `created_at`. При одинаковой дате сохранять устойчивый порядок. Не скрывать секцию при нуле непрочитанных.
- Счётчик — «Новых: N»; если новых нет — «Новых сообщений нет». Счётчик означает непрочитанные, а не размер истории.
- Карточка сохраняет заголовок, дату и текст. Непрочитанная содержит существующее действие «Понятно» / «Рейс принят». После успешного подтверждения карточка остаётся на месте, действие заменяется текстом «Прочитано»; прочитанность не обозначать одной только прозрачностью или цветом. Не снижать opacity всей карточки.
- Пустая история: «Сообщений пока нет» и пояснение «Здесь появятся назначения рейсов и сообщения от офиса». Секция синхронизации остаётся независимой.
- Не обрезать историю молча до 20 записей: если нужен предел DOM, кнопка «Показать ещё» по 20 из уже полученных данных. Не обещать бессрочную историю сверх данных API.
- Пока запрос подтверждения выполняется — блокировать только его кнопку, текст «Сохраняем…». При отказе карточка остаётся непрочитанной, рядом постоянная ошибка и «Повторить». Без сети сохранять действующее ограничение сервера/клиента, не объявлять сообщение прочитанным до успешного ответа.
- Polling не возвращает прочитанные в новые, не сбрасывает раскрытую порцию истории и фокус. Подтверждение не должно отправлять фокус на body: сохранить его на карточке/её статусе; статус изменения сообщить через существующий live region.

Приёмка: прочитать все сообщения → история остаётся; обновить страницу → прочитанность сохранена; пустой массив → понятное пустое состояние; ошибка API → доступен повтор. Проверить телефон и desktop, обе темы.

## F08 — «Смотреть все задачи»

Минимальное решение без новой страницы: раскрыть полный список в существующей карточке «Задачи» на Обзоре.

- Один общий массив задач строить **до** любых `.slice()`: просроченные оплаты, непроверенные расходы, рейсы на проверке (`pending_review`, `needs_explanation`), активные/назначенные рейсы. Сохранить существующие условия включения и приоритет этих групп.
- Свернуто показывать до шести задач текущего фильтра. «Смотреть все задачи» сбрасывает фильтр в «Все», раскрывает все задачи всех четырёх типов и остаётся на Обзоре. Не переходить в расходы. После раскрытия — «Свернуть список»; свернуть до шести без смены маршрута и фокуса.
- Фильтры «Все» / срочность продолжают работать по полному массиву. Выбранное состояние доступно программно (`aria-pressed`); раскрытие — `aria-expanded` и `aria-controls` списка.
- Каждая строка сохраняет существующий переход: оплата → заказчики; расход → расходы; рейс → конкретный рейс. Не терять доступные задачи из-за лимита два на группу.
- Нет задач: «Сейчас задач нет». Пустой фильтр: «В этой группе задач сейчас нет» и действие «Показать все задачи». При нуле задач кнопку раскрытия скрыть; при шести или менее можно её скрыть, если выбран «Все».
- Polling сохраняет раскрытие, фильтр и фокус. На телефоне список увеличивает высоту страницы, без вложенного вертикального скролла. Кнопка остаётся в конце карточки.

Приёмка: данные со всеми четырьмя типами и более чем двумя задачами на тип; раскрытие показывает все, фильтры не теряют задачи; переходы верны; свертывание и обновление не меняют контекст.

## F10 / F03 — постоянные ошибки форм

- Использовать существующую форму и label. Сразу под проблемным полем — текст `.field-error` с устойчивым уникальным `id`. На control: `aria-invalid="true"`; error-id добавить к `aria-describedby`, сохраняя id подсказок. Цвет дополняет текст «Ошибка: …».
- Валидация при submit и повторная проверка уже ошибочного поля при input/change; не показывать ошибку на нетронутом поле при первом открытии. Очищать ошибку после успешной проверки именно этого поля, не автоматически от любого ввода.
- Для `12,345`: «Ошибка: укажите сумму с точностью до копеек, например 12,34». Для пустой обязательной суммы: «Ошибка: укажите сумму». Сохранять введённое значение и остальные поля.
- Одна ошибка поля — фокус на него после submit. Несколько ошибок — видимый `.form-error-summary` в начале формы с заголовком «Проверьте поля» и ссылками на ошибочные поля; `tabindex="-1"`, фокус на сводку. Не дублировать одновременно несколько assertive-объявлений.
- Ошибки API, не связанные с одним полем: постоянный `.form-error` рядом с областью отправки, `role="alert"`; понятный текст причины и способ повтора. Не вкладывать ошибки в скрытый блок. Toast допускается как дополнение.
- Диалог не закрывать до завершения валидации **и успешного ответа**. На 4xx/сети/5xx сохранять диалог, значения, причину и файлы; после ошибки вернуть возможность повторить. Устойчивые ключи финансовых команд и согласование потерянного ответа сохраняются.
- Отправка: кнопка блокируется, подпись «Сохраняем…», ширина и позиция стабильны. При успехе действующий сценарий закрытия/очистки; при отмене — существующее явное действие пользователя.
- В первую очередь: диалог корректировки ставки, разовые расходы, переводы и другие формы с `rublesToKopecks`; тот же контракт для start/complete/expense водителя и обязательных файлов. HTML/ARIA и жизненный цикл ошибок — ответственность разработки.
- CSS-контракт: `.field-error`, `.form-error`, `.form-error-summary`, `[aria-invalid="true"]`; использовать `--danger`, `--accent-soft`, `--line`, `--focus` с темизацией. Не уменьшать текст ошибки ниже окружающей подсказки, не использовать абсолютное позиционирование.

Приёмка: дробная копейка, пустая сумма, API 4xx/5xx и сетевой отказ; исправление и успешный повтор; клавиатура и связи ARIA; диалог/файлы/черновик не теряются. Сохранить нативную required-валидацию там, где она уже действует.

## F11 — явное завершение рейса

- На экране «Рейс» для `in_progress` в существующем блоке быстрых действий: основной «Добавить расход», видимый вторичный «Завершить рейс», затем менее заметный «Детали рейса»; «Фото чека» сохранить. Минимум 44×44 CSS px, без горизонтального переполнения, перенос строк действий допустим.
- «Завершить рейс» раскрывает существующую форму завершения, прокручивает к заголовку «Завершение рейса» и переводит туда фокус (`tabindex="-1"`). Это **открытие формы**, без немедленной отправки или дополнительного диалога подтверждения.
- На Главной кнопку существующего перехода к активному рейсу назвать «Завершить рейс» и вести сразу к этой форме. «Добавить расход» остаётся главным действием частого сценария. Не подменять кнопку доступа к деталям единственной возможностью завершить рейс.
- Форма сохраняет время разгрузки, конечный одометр и оригинал фото. Кнопка отправки «Завершить рейс». Для назначенного/завершённого рейса действие завершения не показывать; применить существующие ограничения syncing/отклонённой очереди, не обходить их.
- Без связи остаётся действующая офлайн-очередь; после локального сохранения показывать «Завершение сохранено на телефоне. Отправим при появлении связи», не «Рейс подтверждён». Подтверждение офиса остаётся отдельной операцией.
- Polling не сворачивает открытую форму и не очищает черновик. Скрытие деталей не должно скрывать отдельно раскрытую форму завершения.

Приёмка: повторно открыть активный рейс → «Завершить рейс» видно без раскрытия деталей; открыть с Главной и из «Рейс»; проверить фокус, заполнение, ошибку, отмену/возврат и существующую очередь. На назначенном/завершённом рейсе недопустимое действие отсутствует.

## Общая проверка

Обе темы; 360×800, 390×844, 768×1024, 1280×800. Текст ≥4,5:1, крупный текст и значимые элементы ≥3:1, видимый фокус ≥3:1 к соседней поверхности. Без горизонтальной прокрутки; клавиатурный доступ и текстовые статусы. Физические устройства, Safari и реальная камера — отдельная полевая проверка, не обещание этой спецификации.
